# How-to: Database (Prisma + PostgreSQL)

Persistence is PostgreSQL through Prisma 7. The schema lives in
`apps/api/prisma/schema.prisma` and the migrations in `apps/api/prisma/migrations/`.

Run every command from the repo root with `--filter @cenzontle/api` (or from
`apps/api/`). They all need `DATABASE_URL` in `apps/api/.env`.

---

## Essential commands

```bash
# Generate the Prisma client (automatic on postinstall/predev, but just in case)
pnpm --filter @cenzontle/api exec prisma generate

# Apply pending migrations (WHAT YOU NORMALLY USE)
pnpm --filter @cenzontle/api exec prisma migrate deploy

# Show migration state (what's missing, drift)
pnpm --filter @cenzontle/api exec prisma migrate status

# Seed sample data (idempotent, deletes nothing)
pnpm --filter @cenzontle/api exec prisma db seed

# Open Prisma Studio (visual database browser)
pnpm --filter @cenzontle/api exec prisma studio
```

---

## `migrate deploy` vs `migrate dev` — use deploy

- **`migrate deploy`** — applies only the pending migrations, **never resets**, and
  is not interactive. It is the right one for bringing up local and for production.
- **`migrate dev`** — for **creating** a new migration after you edit the schema. It
  runs drift detection and may offer to **reset the database** (destructive). Use it
  only when you are changing the schema, and read what it proposes.

```bash
# Only when you MODIFY schema.prisma and want a new migration:
pnpm --filter @cenzontle/api exec prisma migrate dev --name description_of_the_change
```

> Migrations are generated by Prisma; **do not hand-edit the `.sql`** except for
> things Prisma cannot express (for example partial unique indexes in raw SQL, which
> this repo does use — see `CREATE UNIQUE INDEX ... WHERE` in
> `apps/api/prisma/migrations/20260613000000_add_qa_pipeline/migration.sql`).

## The seed

`apps/api/prisma/seed.ts` creates a small sample dataset so there is something to
look at on first boot: 2 Pods (`Plataforma`, `Experiencia Web`), 1 initiative,
1 epic, its 2 epic↔Pod rows and 3 stories.

It is **idempotent and additive**. Everything is written with `upsert` against fixed
ids (or against `Pod.name`, which is UNIQUE), so running it twice leaves the database
in the same state. It **never deletes**, and it never overwrites a row it did not
create. Two deliberate choices make that true:

- **Pods are matched by name and left alone if they already exist.** `Pod.name` is a
  natural key your team may already be using, so the `upsert` carries an empty
  `update`: if a Pod called `Plataforma` is already yours, the seed reuses it for the
  relations and touches neither its description nor its color.
- **The epic `upsert` updates only descriptive fields.** The Forge timestamps are left
  untouched, so re-running the seed cannot resurrect or overwrite the state of a batch
  in flight.

Two things worth knowing about what it writes:

- **It does not seed the Definition of Done (DoD) catalog.** The `dod_criteria` rows
  are populated by migrations (`20260508233000_add_dod_criteria`,
  `20260508250000_dod_evidence_based_defaults`); `DodService.resetDefaults()` is the
  only other legitimate writer.
- **It writes the epic's markdown body, but no vault path.** `Epic.markdown` is a real
  Postgres column (`apps/api/prisma/schema.prisma:98`) and the seed fills it with the
  full nine-heading epic document (`apps/api/prisma/seed.ts:163,169` — the `update` and
  the `create` branch of the same `upsert`). Stories work differently: `Story` has no
  markdown column (`schema.prisma:214-275`), so story prose lives only in the
  [vault](glossary.md#vault) as markdown in GitHub. Either way the seeded rows leave
  `vaultPath` null — the seed never touches the vault repository.

→ Everything else (more Pods, initiatives, epics, stories) you create **from the UI**
once you are logged in.

## Dual Postgres: native vs Docker

If you already had a **native** PostgreSQL (Homebrew or similar) listening on
`:5432`, the Docker container **will not** be able to map that port — or worse, your
`DATABASE_URL` may point at the wrong Postgres. Typical symptom: "the database is
gone", or tables that appear and disappear depending on which client you connect
with.

**Before you assume data loss**, check WHO is listening on :5432:

```bash
lsof -i :5432            # native postgres, Docker, or both?
docker compose ps        # is the container running?
```

Your options:

- **Docker only:** stop the native Postgres (`brew services stop postgresql`) and let
  the container take `:5432`.
- **Native only:** don't start Docker's postgres service; create the database and the
  role by hand with the credentials from your `DATABASE_URL`.
- **Both at once:** map the container to another port (`"5433:5432"` in
  `docker-compose.yml`) and point `DATABASE_URL` at `:5433`.

`migrate deploy` always applies to the database in `DATABASE_URL` — make sure that is
the one the API actually uses.

## Drift in the migration history

This repo grew with a hybrid of `db push` and migrations, so a database may have
migrations applied that are not in the folder (you'll see it in `migrate status` as
*"migrations from the database are not found locally"*). That does **not** block
`migrate deploy` — deploy only goes folder → database, applying whatever is missing.
Do not run `migrate reset` to "fix" drift on a database with real data.

## Common errors

| Symptom | Cause | Fix |
|---|---|---|
| `relation "..." does not exist` (P2021) | Migrations not applied | `prisma migrate deploy` |
| `PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL` | Missing `.env` | `cp apps/api/.env.example apps/api/.env` and fill it in |
| `Can't reach database server` | Postgres isn't up, or wrong port | `docker compose up -d postgres` / check the port |
| The API started but queries fail after you add models | Stale Prisma client in memory | restart `pnpm dev` (regenerates and reloads the client) |

More in [troubleshooting.md](troubleshooting.md).
